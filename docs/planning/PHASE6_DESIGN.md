# Phase 6 implementation boundaries

Base: `98756a9e33da0ef6c9ed38bda177b7cb910c7855`; branch:
`feat/v1.1-phase6-customer-offline`. This working design accompanies the approved
Phase 6 request; G6 acceptance remains pending. No merge or later phase is authorized.

## Product slice

Keep the existing challenge-local customer journey and numerical behavior. Link its
preparation page to a dedicated `/preparedness/` entry point using the same React/Vite
application conventions. A separately scoped shell avoids caching the challenge
dashboard, private responses, maps, declarations or provider integrations.

The generic reviewed kit is always readable and printable. The fictional power-path
journey uses the unchanged six Phase 1 definitions. Python prepares bounded milestone
frames using the existing fixed release/person-hour baseline, G2 schedule validation
and release rules. No stochastic simulation, optimizer tuning or new simulation API.
The browser selects an already computed frame; it never calculates release counts,
repair durations or risk. Serving immutable prepared frames is distinct from claiming
the Phase 1 catalog API now performs numerical evaluation.

Fetch active mode and the pinned catalog metadata with no-store semantics. Saving and
online scenario selection require positively verified synthetic mode and matching
scenario input/artifact fingerprints. Unknown mode and challenge-local fail closed.
Do not silently replace a failed live load with a saved view. Saved views open explicitly,
as historical fiction, with timestamps and versions. Offline controls cannot create a
new numerical result. Reconnection is an explicit refresh and revalidation.

## Power-path semantics

Render only authored path edges, in supplied order; unresolved edges stay explicit.
An abstract supply terminal has no geographic position. Non-repair equipment is an
intact assumption, never an observed healthy asset. Listed repairs begin as declared
damage; blocked work and blocked prerequisites remain distinct from unknown evidence.
Completed states refer only to a selected precomputed milestone. Customer release
requires every declared damaged dependency, and unknown links cannot become restored.

Use native labeled buttons and ordered lists for a keyboard-operable schematic and
dependency details. The same selection highlights a shared repair in every affected
fictional path and its details. All states have text labels, visible focus and narrow-
screen layouts; no pointer-only graph, inferred facility attachment or animated power flow.

## Persistence and cache boundaries

Use one versioned snapshot key and explicit save/delete/reset controls. Persist only a
strictly validated fictional frame, its model/policy/input/result versions/fingerprints
and save timestamp. Runtime schema checks reject extra fields; content fingerprints
must also match build-approved frames, preventing arbitrary free text or source content
from being smuggled into a structurally valid record. Never persist raw API responses,
customer declarations, contact details, real geometry, credentials or challenge topology.

Precache only the generic kit and minimum compiled shell assets through a build-generated
exact allowlist and integrity checks. Worker scope is `/preparedness/`; API calls, POSTs,
external tiles and arbitrary URLs are excluded. Prepared fictional frame downloads are
not automatically cached. Only explicitly saved eligible frames enter snapshot storage.
Show offline-ready only after the worker confirms required entries are present and valid.
Storage/worker failures leave a printable/downloadable generic kit and honest status.

Cache versions follow content hashes; updates must not combine mismatched shells and
schemas. Unknown snapshot versions are rejected rather than guessed. Reset removes only
GridGuide preparedness data, verifies removal and reports denied deletion. Cross-tab
changes invalidate the displayed saved state. No automatic background snapshot creation.

## Evidence and required verification

Real browser tests must exercise production builds, actual persistent browser restart,
network denial, mode changes, schema/corruption/privacy rejection, storage failure,
deletion, cache upgrades and out-of-scope requests. Include automated serious/critical
accessibility checks, keyboard/mobile/reduced-motion tests and authentic screenshots.
Manual screen-reader work is pending unless actually performed; automation is not WCAG
certification. Existing Python/browser/golden/source/legacy/G2–G5 checks remain required.
G5 artifact checks replace unnecessary Monte Carlo reruns because numerical code is untouched.

Preserve G3's failed promotion target/default baseline and G4's evidence-bounded No-Go.
No G5 quantiles are displayed without approved artifact/contract support. Future operator
integration must retain stable/unstable/unresolved/unsupported distinctions, all regressions,
and synthetic-assumption labels; no current UI claim of calibrated ETRs is permitted.
